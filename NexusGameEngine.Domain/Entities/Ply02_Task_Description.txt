=== TASK [PLY-02] Implementazione Cooldown Azioni In-Game (TimeProvider) (Epic 3) ===

OBIETTIVO: 
Introdurre un sistema di limitazione temporale (cooldown) per azioni specifiche del giocatore 
(es. "Claim Daily Reward" o "Usa Abilità"), rendendo il tutto unit-testabile.

REQUISITI TECNICI STRICT: 
- Devi usare l'astrazione nativa .NET 8/9/10 TimeProvider iniettata nei Command Handler.
- Effettuare test isolati (Unit Test) con FakeTimeProvider.

----------------------------------------------------------------------
SUDDIVISIONE DEI LAVORI (PIANO D'AZIONE)
----------------------------------------------------------------------

PASSO 1: MODELLAZIONE DEL DOMINIO (Entità Player) :::::: CHIUSO
- [ ] Creare il Value Object (C# record) `PlayerCooldown` con le proprietà `ActionId` (stringa) e `ReadyAt` (DateTimeOffset). Non avrà Identity (`Id`) né Foreign Key (`PlayerId`) per mantenere puro il dominio.
- [ ] Aggiungere al `Player` una collezione per tracciare i cooldown (es. `List<PlayerCooldown>`).
- [ ] NOTA ARCHITETTURALE (Per Epic 3): EF Core 10 mapperà questa lista tramite `builder.ComplexCollection()`. Questo memorizzerà l'intera collezione in una singola colonna JSON all'interno della tabella `Players`, eliminando la necessità di tabelle separate, Shadow Properties o chiavi esterne.
- [ ] Creare un metodo di dominio in `Player` (es. `Result<bool> TryStartCooldown(string actionId, DateTimeOffset readyAt, DateTimeOffset currentTime)`).
- [ ] Se il `currentTime` è minore del `ReadyAt` registrato per quell'azione, restituire un errore tipizzato: `Error.Conflict("Cooldown.Active", "Azione non ancora disponibile")`.
- [ ] Se disponibile, aggiornare o inserire il nuovo cooldown sostituendo quello vecchio.

PASSO 2: SETUP CQRS E INJECTION DEL TIMEPROVIDER :::::: CHIUSO
- [ ] Creare i casi d'uso (`ClaimDailyRewardCommand` e `ClaimDailyRewardHandler`; UseSpecialSkillCommand e UseSpecialSkillHandler).
- [ ] Iniettare l'interfaccia nativa `TimeProvider` nel costruttore dell'Handler, insieme a `IApplicationDbContext`.

PASSO 3: IMPLEMENTAZIONE DEGLI HANDLER

PASSO 3A: Logica di `ClaimDailyRewardHandler` (Loot Randomico) :::::: CHIUSO
- [ ] Recuperare il `Player` dal DB includendo i cooldown (`Include(p => p.Cooldowns)`).
- [ ] Ottenere l'ora esatta con `_timeProvider.GetUtcNow()` e calcolare la mezzanotte del giorno successivo.
- [ ] Chiamare `player.TryStartCooldown(GameConstants.Actions.ClaimDailyReward, mezzanotte, currentTime)`. Se fallisce (es. premio già riscosso), ritornare l'errore.
- [ ] Implementare la Roulette Randomica con `System.Random.Shared.Next(0, 100)`:
      - **Caso Soldi (0-49):** Pescare un valore a caso dall'array `[100, 200, 500, 1000]` e chiamare `player.AddMoney(valore)`. Popolare il DTO con `MoneyGained`.
      - **Caso Oggetto (50-99):** Query al DB per un `Item` casuale (`OrderBy(Guid.NewGuid()).FirstOrDefaultAsync()`). Creare un `InventorySlot` e chiamare `player.AddInventorySlot()`. Popolare il DTO con `ItemNameGained` e `ItemAmountGained`.
- [ ] Chiamare `_context.SaveChangesAsync()`.
- [ ] Restituire il DTO popolato.

PASSO 3B: Logica di `UseSpecialSkillHandler` :::::: CHIUSO
- [ ] Recuperare il `Player` dal DB includendo i cooldown (`Include(p => p.Cooldowns)`).
- [ ] Verificare che il giocatore abbia una skill equipaggiata (`player.ActiveSpecialSkill.HasValue`). Altrimenti, ritornare errore.
- [ ] Ottenere l'ora esatta con `_timeProvider.GetUtcNow()` e aggiungere la durata fissa del cooldown: `currentTime + GameConstants.ActionCooldowns.UseSpecialSkillCooldown`.
- [ ] Chiamare `player.TryStartCooldown(GameConstants.Actions.UseSpecialSkill, nuovaData, currentTime)`. Se fallisce (skill in cooldown), ritornare errore.
- [ ] *Nota per Epic 4*: Per adesso l'azione della skill non fa nulla di effettivo al mondo di gioco, simuliamo solo il successo.
- [ ] Chiamare `_context.SaveChangesAsync()`.
- [ ] Restituire `Result.Success(true)`.

PASSO 4: CREAZIONE DEGLI ENDPOINT (MINIMAL API) :::::: CHIUSO
- [ ] Creare gli endpoint nel livello API per esporre i comandi.
- [ ] Endpoint POST `/api/players/claim-daily-reward`: Invia il `ClaimDailyRewardCommand` a MediatR.
- [ ] Endpoint POST `/api/players/use-special-skill`: Invia il `UseSpecialSkillCommand` a MediatR.
- [ ] Assicurarsi che la risposta HTTP mappi correttamente il `Result` (es. restituendo 409 Conflict o 400 Bad Request se il comando fallisce per via del cooldown).

PASSO 5: UNIT TESTING E FAKETIMEPROVIDER
- [ ] Creare una classe di Unit Test (es. `ClaimDailyRewardTests`) usando `xUnit` e `Moq` (per mockare il DB, trattandosi di unit test).
- [ ] Istanziare un `FakeTimeProvider` (dal pacchetto `Microsoft.Extensions.TimeProvider.Testing`).
- [ ] TEST A: Lanciare l'handler -> Successo.
- [ ] TEST B: Rilanciare l'handler immediatamente -> Fallimento (Cooldown Attivo).
- [ ] TEST C: Avanzare il tempo artificialmente di 24 ore (`fakeTimeProvider.Advance(TimeSpan.FromHours(24))`) e rilanciare l'handler -> Ritorna al Successo!

PASSO 6: DEFINITION OF DONE (DoD) - Criteri di Accettazione
- [ ] Il codice compila senza warning.
- [ ] L'uso di DateTime.Now o DateTime.UtcNow è rigorosamente vietato nel livello Application/Domain.
- [ ] Il sistema respinge l'azione con un errore Error.Conflict.
- [ ] Lo Unit Test simula con successo l'avanzamento del tempo tramite .Advance().
